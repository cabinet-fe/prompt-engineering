# 库技能标准

## 为什么

AI大模型/智能体 通常对于开源的库和项目进行了足够的训练, 所以使用这些库或者项目时会非常得心应手, 准确率相当高.

但对于企业私有库或者小众开源项目, AI大模型/智能体 便无法准确的使用它们了, 本技能用于指导 智能体/AI 为此类库生成高效、准确的`文档型`技能.

## 目标

创建**专给 智能体/AI 使用**的、 **库**的"操作手册", 帮助其准确、高效的使用该库.

## 硬约束

- **事实来源**：API、签名、约束、示例必须来自公共导出、类型声明、源码、测试、示例、README、CHANGELOG；禁止用训练数据或猜测补齐。
- **仅公共 API**：排除 `internal`、`private`、未导出、标注 `@internal` / `@private` 的符号。
- **渐进披露**：`SKILL.md` 精简；细节放入`references/`或者类似的目录中，按需加载。
- **技能语言**: 使用中文, 避免使用英文.
- **文档边界**: 禁止将库的内部实现细节写入文档, 关注 API 本身.

## 目录结构

### 简单库示例

```text
<skill-name>/
├── SKILL.md
└── references/
    ├── index.md             #  入口, 提供资源的导航以及概括说明, 同时引用apis.md和examples.md
    ├── apis.md             #  API定义, 包含API的签名、参数、返回值
    └── examples.md        # 一些使用示例.
```

### 单体仓库示例

```text
<skill-name>/
├── SKILL.md
└── packages/
    ├── package1/
    │   ├── index.md            #  入口, 提供资源的导航以及概括说明, 同时引用apis.md和examples.
    │   ├── apis.md              #  API定义, 包含API的签名、参数、返回值
    │   └── examples.md          # 一些使用示例.
    └── package2/
        ├── modules1/             #  模块分组
        │   ├── index.md            #  入口, 提供资源的导航以及概括说明, 同时引用apis.md和examples.
        │   ├── apis.md              #  API定义, 包含API的签名、参数、返回值
        │   └── examples.md          # 一些使用示例.
        ├── modules2/
        │   ├── index.md
        │   ├── apis.md
        │   └── examples.md
        └── .../
```

## 工作流

### 新增

1. 分析目标库的源码、测试、文档, 确定文档粒度(有的库可能粒度非常细, 一个方法一个文件, 这时就应该以一个更粗的粒度对这些方法进行分类), 并向用户进行确认.
2. 向用户确认技能名称
3. 按源码、测试为第一优先级,库的文档(如有)为补充去生成技能, 技能的 `references/` 目录(对于多包的单体仓库更推荐使用`packages/`目录)存放渐进式披露的文档.

### 更新

步骤一: 先分析既有技能是否符合本技能中的规范, 如果不符合则向用户确认是否进行重写.

1. 如果需要重写, 则按照新增的步骤进行.
2. 如果不需要重写, 进入 步骤二.
   步骤二: 按需求和规范更新技能内容.

## 输出落点

除非硬性指定, 库的伴生技能通常放在`skills/`目录下. 结构为: `skills/<skill-name>/`

## SKILL.md 模板

```markdown
---
name: <skill-name>
description: 使用描述以及何时使用
---

# <库显示名> 使用技能

{技能介绍说明}

## 版本

{精确版本}

## 模块地图/分包地图

{如果是比较大的单体仓库,或者库分了很多功能模块, 在此处进行各个包或者模块的粗略介绍完成最初决策}

## 路由决策

{用户意图 → 推荐工作流 / API}

## 检查清单

- 是否已安装
- 安装的依赖版本是否匹配
- ...
```

## 自动更新

库代码更新后，伴生技能必须同步更新。

更新清单:

1. **读现有 skill**：记下当前声称的版本与 API。
2. **对照事实源**：diff 或重读公共入口、类型、测试、示例、CHANGELOG；只采公共 API。
3. **增量修订**（避免无故推翻可用结构）：更新版本；修正签名/导入/示例；调整任务决策与「何时读 reference」；改写受影响的 references；标注弃用并指向替换。
4. **跑验证**（下一节）后再交付。

## 验证

- [ ] 确保所有 `references/`(或者`packages/`) 目录下的所有文件都有对应的决策路径可以路由到
- [ ] 示例与签名仅使用公共 API，且与当前库版本一致
- [ ] `SKILL.md` 足够精简, 不要超过200行

## 反模式

- 把整本 API 手册塞进单个 `SKILL.md`
- 为每个导出函数创建独立 Skill
- 无加载条件地罗列 `references/`(或者`packages/`)
- 示例使用内部路径或未导出符号
- 用过时训练知识填写「推荐 API」
- 库代码已变却不更新伴生技能
- 在事实已足够时反复向用户确认琐事
