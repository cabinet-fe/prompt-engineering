# explore

需求已经明确时不要用本技能，让用户显式调用 `to-spec`。这里只处理含糊需求，或改一个尚未归档单位的需求。不写 spec、不改代码。禁止啰嗦和故作高深。CONTEXT 必须与仓库现状对齐。

## 前置检查

运行 `node .agents/scripts/precheck.mjs`：FAIL 则停止，按输出提示用户执行 `setup`，不要代跑。PASS 输出携带项目类别；按根 AGENTS.md 按需读 docs。

## 统一工具定义

- **<@交互式提问>**：语义命中「提问 / 选择 / 确认」的工具即调用；没有则用文本提问。禁止伪造工具调用。

## 单位

一次只做一个 `cooking/<feature>/`。其它单位未完成也可以新开。

新开或改范围：只读其它未归档单位的 `goal.md` 做冲突检查（没有 goal 则只看 `spec.md` 标题）。冲突未解决不新建。用户一次说了多件不相关的事：问清本次是哪一件。

改**同一个**已有 `spec.md` 或 `tasks/` 的单位（不是新开）：立刻把该 goal 的确认改为 `未确认`；问补充 / 改写 / 取消。取消则改回 `已确认`，下游不动。确认新目标后：把各 `tasks/P*.md` 的「状态」抄进纪要，删除该单位的 spec/tasks/reviews，不回滚代码。其它 cooking 单位一律不要动。

## 决策树

核心是钉死全部**有歧义**的点、跟用户同步心智：凡是「不问就可能做错」的歧义都要问到。开局先把当前能想到的歧义逐条写进 `goal.md` 的「未决问题」（用户已答或仓库事实可查的不算）。对象、目标、边界、约束、冲突只是常见自查角度，不是固定轮次，也不限于此：简单需求可能一轮就够，复杂需求轮次不设上限。不要把后续轮次的具体问题预先写进 `goal.md`。

每一轮：

- 从未决歧义里挑最阻塞的问；不要为凑数而问；一轮最多 5 题。
- 按 [question-template.md](references/question-template.md)，经 <@交互式提问> **单独出现**（本轮不要夹带下一轮预告，不要把未决清单当问卷一次倒给用户）。
- 用户答完才能决定下一轮的具体问题；讨论中新冒出的歧义随时补进「未决问题」。
- 查得到的事实派子代理，不问用户。子代理未返回时：只挡住依赖该事实的问题，本轮其余照问。

范围边界（包含 / 不包含）尽早钉死，禁止「范围以后再说」。

不要问拆任务、改哪些文件、验收条文案。

## 退出

「未决问题」清零才停：没有默许的假设。把「需求目标 + 范围」交给用户确认后，才写 `确认：已确认`。未确认前每轮按 [goal-template.md](references/goal-template.md) 回写，不得增删标题。对话纪要只写已钉死结论，禁止复述问答、禁止复制决策树。
