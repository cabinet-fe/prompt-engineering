# explore

需求已经明确时不要用本技能，直接 `to-spec`。这里只处理含糊需求，或改一个尚未归档单位的需求。不写 spec、不改代码。

## 前置检查

未完成 setup 则停止，告诉用户先执行 `setup`，不要代跑。判定与其它工程技能相同。

## 使用工具

- **<@交互式提问>**：语义命中「提问 / 选择 / 确认」的工具即调用；没有则用文本提问。禁止伪造工具调用。
- **<@子代理>**：查仓库事实时派独立子代理。禁止伪造调用。

## 单位

一次只做一个 `cooking/<feature>/`。其它单位未完成也可以新开。

新开或改范围：只读其它未归档单位的 `goal.md` 做冲突检查（没有 goal 则只看 `spec.md` 标题）。冲突未解决不新建。用户一次说了多件不相关的事：问清本次是哪一件。

改**同一个**已有 `spec.md` 或 `tasks/` 的单位（不是新开）：立刻把该 goal 的确认改为 `未确认`；问补充 / 改写 / 取消。取消则改回 `已确认`，下游不动。确认新目标后：把各 `tasks/P*.md` 的「状态」抄进纪要，删除该单位的 spec/tasks/reviews，不回滚代码。其它 cooking 单位一律不要动。

## 决策树

研讨映射成一棵决策树，写在 `goal.md`。**前沿**是前提已定、现在就能问的问题。每一轮把整条前沿问完（<@交互式提问>，每问给推荐答案），等用户回答再进入下一轮。

如果某个问题的答案取决于本轮还没回答的另一个问题，那它属于后面的轮次，不是这一轮。前面的轮次钉具体边界（包含 / 不包含），禁止「范围以后再说」。

查找事实派独立子代理，不要问用户能查到的东西。子代理未返回时：只挡住依赖该事实的问题，前沿其余问题照问。决策问用户。

不要问拆任务、改哪些文件、验收条文案。

## 退出

前沿空了就停：分支走完，没有默许的假设。把「需求目标 + 范围」交给用户确认后，才写 `确认：已确认`。未确认前每轮按 [goal-template.md](references/goal-template.md) 回写，不得增删标题。
