# 代码项目访谈

分类已写入 `PROJECT.md` 之后、落盘 `ARCHITECTURE.md` / `DEV-STANDARDS.md` / `CODE-MAP.md` 之前使用。非代码不要走本文。

提问一律使用 `交互式提问` 工具。每轮最多 3～5 题，等答完再问下一轮。禁止一次甩出长问卷。按类别出题，不要把 Web 全家桶甩给库或 CLI。

**现有项目**以仓库为事实来源：仓库已经回答的不问（例如 lockfile 里的语言、已有 eslint 就引用配置）。架构叙事、模块边界、必须人定的规范，仍要多轮澄清，禁止把推断写成既成事实。

用户说「先按惯例 / 先这样」：停追问，能写的写入，其余进 `ARCHITECTURE.md`「未决」。用户拒绝的章节：不写进 `DEV-STANDARDS.md`，列入 `ARCHITECTURE.md`「未决」。

## 架构轮（写 `ARCHITECTURE.md` 之前）

### 1. 产品

做什么、给谁用、核心域。

现有项目：先给一版从代码/README 归纳的草稿，只问空白和矛盾。新项目：不知道的才问。

### 2. 技术边界

进程/服务怎么切、数据在哪、关键集成。

全栈：若 `PROJECT.md` 还没有架构形态，先锁形态并写回 `PROJECT.md`，再问 API 风格、鉴权落在哪一端、是否有 BFF。已有形态则直接问未落地的边界。

### 3. 技术栈

只问上一轮还没落地的层。不适用的行不要出现在表里，也不要问。现有项目能从 lockfile / 构建配置读到的层直接写入，标清来源，不要装成用户刚定的。

### 4. 追问

根据已答追缺口（选了分离却没说 API；monorepo 却没说包职责）。直到能落盘或用户叫停。

## 规范轮（写 `DEV-STANDARDS.md` 之前）

只问代码/配置里看不出来、必须人定的。无依据的章节整节删除，不留空标题。

### 1. 通用

命名、注释语言、测试何时必须写、明确禁止。

### 2. 按类别补一轮

- 前端项目：组件目录、状态归属
- 后端项目：错误码、日志、迁移
- 前端库 / 后端库：公开 API 稳定性、兼容范围
- 全栈项目：前端一轮 + 后端一轮；不要把库的 API 稳定性问题甩给应用

### 3. 「先按惯例」

写明采用该语言/框架的主流惯例，禁止编造独特规范。已有 prettier/eslint/editorconfig 就引用配置，不要复述。

## 地图（写 `CODE-MAP.md`）

模板见 [templates.md](templates.md)。何时改、改哪、何时停见 [code-map-update.md](code-map-update.md)。

- **现有项目**：扫真实目录生成树/模块表/依赖图。**模块怎么切拿不准才问**（一个包算一行，还是 `src/` 子目录算一行）。
- **新项目**：按组织结构写规划目录，问用户模块切分是否对，再落盘；尚未建目录就标明「规划」。

## 写入

回答写入对应 docs，不要堆进 `AGENTS.md`。`PROJECT.md` 只在类别、组织结构、全栈形态变化时改。
