# 访谈

使用 `交互式提问` 工具。每轮最多 5 题，等答完再问。只问检索之后仍不明的。不要把 setup 的架构/规范访谈搬过来，也不要回写 `interview.md`。

选项至少 2 个；必须收集、且规格禁止默认的题，推荐填「无」。

## 各类都可能问

- 是不是纯原型或日常工作（仓库已能判定则不问）
- 要验收的关键路径 / 关键接口 / 关键页面（按类别收窄，不要甩全家桶）

## 按类别

检索已经回答的跳过。

**前端项目**：关键用户路径。已有 e2e 则问是否沿用（默认沿用，用户要换才换）。

**后端项目**：HTTP 入口（base URL 或本地怎么起）。选 HTTP 脚本则**必须**问鉴权（无鉴权 / Cookie / Bearer / 自定义头 / 其它），禁止代填。看起来像微服务：问入口服务是哪一个；列出仓库里能看到的 compose，问哪些算在内。关键 HTTP 用例。

**全栈 · 分离**：后端一轮 + 前端一轮。鉴权规则同后端。

**全栈 · 一体**：关键页面 + 要测的 API 路径。鉴权若 API 测需要，同样必问、无默认。

**前端库 / 后端库**：确认沿用哪条已有测试命令。是否加 pack 干跑（可选，不默认加）。

**App**：平台（iOS / Android / 都有）。已有 UI 测则问沿用哪条命令；否则走 Maestro，问 appId 与关键流程。

**嵌入式**：host 上跑哪条测试命令。不要主动推销 HIL；用户自己提 HIL 且本机/硬件不具备 → 标跳过，不写成必过。

**游戏**：引擎 Test Runner 怎么调。搜不到入口则告诉用户不落脚手架，不要改问「用不用通用方案」。

**非代码**：已有构建或链接检查则确认沿用；都没有则问要链接检查还是构建（两者都无惯例且用户也不要 → 不落脚手架）。

## 确认推荐

推荐成型后问是否采用。用户改口：只回到已检索事实和 [recommend.md](recommend.md) 表内手段，不编造表外工具。
